# First dry run — 2026-09-09

One real problem, evidence-only, no promotion. Client data stays in the client workspace; this note is de-identified.

## The problem
A deployed voice agent (Vapi) stopped calling its repair-order lookup tool from about 04:00 UTC on one day and told 774 callers "our repair order system is down". The same line had fired on 75 calls three weeks earlier. Question given to the council: was the tool failing, or was it switched off, and what should the agent do next time.

Source: a 970 MB call export (`calls.ndjson.gz`, one JSON call per line, each with the full system prompt used on that call, tool calls and tool results), a snapshot of assistant configs, and an existing findings note written by hand before the plugin existed.

## What the council found
- The drop was a deliberate prompt edit at 04:06:56Z: a dated outage block was inserted into the system prompt of 120 of 134 assistants (each got a version bump), forbidding the three repair-order tools and scripting the "system is down" line. Tools stayed attached: the single attempt after the block (15:38Z) errored `SEARCH_FAILED`.
- Three weeks earlier the same block appeared one hour after a burst of `SEARCH_FAILED` results and was removed about three hours later, before the end date written in the block itself.
- The block already carried a callback-intake fallback. On the outage day, of 864 calls that spoke the line: 372 were offered a callback, 248 transferred, 2 got an SMS, 157 hung up with no further turn.
- The very first call carrying the block (04:06:56Z) still ran the search tool and got a real result, so the tool was reachable with the block in place. The block text itself forbids promising "a callback window, a text, or a notification".
- H1 (upstream API failing all day) was contradicted by its own predicted result and left as the single Unverified claim (C-8). H2 won the only pair judged. Whether the tools were also detached from the assistants (H2 vs H3) cannot be settled from the export: call records carry no tool definitions. That needs a live assistant fetch, which only the user runs.

## What broke (each is in docs/bugs.md with a repro)
1. Silent user → budget copied from a fixture and labelled `set_by: user`. The HANDOFF acceptance line is unreadable as a result: it is the fixture's criterion fields glued together.
2. Plugin agents not registered as subagent types in a checkout session → general-purpose agents with the role file; the frontmatter tool fence is advisory.
3. `retrieve.py` treats bare numbers as query tokens.
4. Run folder holds client data and nothing tells the Supervisor to keep it out of the workspace's git.
5. `report.py` never reads `objections.json`, so a claim under a blocking objection (C-6) rendered as a finding; council.md's rule has no enforcement.
6. No way to supersede a claim: C-5 and C-11 were corrected by C-16 and C-15 but still render as findings next to their corrections.
7. HANDOFF's "Beat:" line names the Elo runner-up (H3, never compared), not the hypothesis actually beaten (H1).
8. Meta-review asked for H1 and H4 to be marked stopped; the Supervisor has no command for that and `hypotheses.json` is Generation-only, so both stay `open` in the table.

## What worked
- `evidence.py` / `claims.py` refusals held: every claim outside Unverified carries evidence ids; the one predicted claim with no evidence stayed visibly unverified through Ranking ("counts for nothing") and into the report.
- The blinded pair worked as designed: the Ranking agent judged from claims and evidence ids only and named the discriminating measurement.
- The fence check (list the run folder after every spawn) was cheap and caught nothing, which is the expected result. Every role produced exactly its own file or reply and nothing else.
- Reflection was the most useful spawn: six of its twelve objections were the same pattern (a number in a claim that appears in no excerpt), and Meta-review named that pattern. Fixing five of them took two minutes of Supervisor work because the evidence was already on disk.
- Frozen goal + budget check gave a clean stop rule; no cap was hit.

## Not done, on purpose
No promotion. No library write. No live API call (the export was already on disk). No spark opened: the H1 contradiction is a refutation, not a surprise that needs a repeat trial. No second Generation round: the refinement Meta-review implied (H2 restated as prompt-only) would have needed a fifth subagent.
